# 01｜看得见屏幕：OCR 与图标检测的双引擎感知

> 「PalatMind 是如何操作电脑的」系列第 1 篇。Agent 要操作屏幕，第一步是把屏幕"读"出来。

[返回目录](../README.md#它是怎么操作电脑的)

## 屏幕上其实只有两类信息

不管界面多复杂，对操作有用的信息就两类：

1. **文字**：菜单名、按钮文字、列表标题、输入框内容
2. **图形元素**：图标按钮（播放三角、放大镜、三个点）、输入框、复选框、滑块

所以感知层用**双引擎**：OCR 负责文字，轻量视觉模型负责图标和控件。两个引擎各司其职，合起来才是完整的"看见"。

## 引擎一：OCR 精准识别页面文字

OCR 的难点不在"能不能识别"，而在**小字、深色主题、复杂背景下的识别率**。我们的工程要点：

**1. 预处理是识别率的一半**

```python
def ocr_screen(img):
    img_x2 = upscale(img, 2)            # 小字号放大 2 倍再识别，最有效的一步
    boxes = ocr(img_x2)
    boxes = scale_back(boxes, 0.5)      # 坐标换算回原始屏幕坐标系
    return [b for b in boxes if b.conf > CONF_THRES]
```

- **放大 2 倍**再送识别：1080p 界面里 12px 的中文小字直接识别错误率很高，放大后大幅下降——这是性价比最高的一步
- **深色主题**：深底浅字与浅底深字混合出现，按区域做自适应反色/对比度增强，不要整屏一刀切

**2. 分层识别**

- 整屏识别一遍拿全局文本
- 对低置信度、小字号的区域**裁剪局部再放大识别一遍**，用局部结果覆盖全局结果
- 代价可控：只有少数区域需要二次识别

**3. 输出必须是结构化的**

每个文本框输出三元组：**文本内容 + 边框坐标 + 置信度**。坐标统一到物理像素（DPI 处理见下篇），低置信度的框保留但标记，由理解层决定是否采用。

**4. 中文场景细节**

- 形近字（未/末、日/曰）靠上下文纠错：结合窗口标题、同区域其他文本联合判断
- 界面上直接复制的文本（如选中列表行）优先走无障碍/剪贴板通道拿原文，OCR 只做兜底——能不猜就不猜

## 引擎二：图标元素小模型

界面上近一半的可点元素**没有文字，只有图标**。OCR 对它们无能为力，需要一个专门的小模型。

**1. 检测：找出"这是个可交互元素"**

用轻量目标检测模型（YOLO 一类的实时架构）在截图上检测 UI 元素框：

- 类别：按钮、输入框、下拉框、复选框、滑块、图标、标签页
- 要求：**单屏推理几十毫秒级**——感知层太慢，整个任务就慢
- 模型小：几百 MB 级别，本地运行，不依赖网络

**2. 语义分类：从"这是个图标"到"这是搜索图标"**

检测只回答"哪里有元素"，还要回答"这个元素是干嘛的"：

- 对检测出的图标做**功能语义分类**：搜索、播放、暂停、关闭、设置、下载、分享、刷新、更多……
- 常用图标就几十类，小分类模型即可覆盖绝大多数场景
- 有了语义，Agent 才能理解"找搜索功能"该点哪个框

**3. 数据从哪来**

公开 UI 数据集打底 + 自采真实应用截图标注补充。关键是覆盖常见控件风格：不同主题（深/浅）、不同缩放（100%/150%）、不同 DPI 下同一图标长相不同，训练数据要覆盖这些变化。

## 双引擎合并：屏幕候选元素集合

两个引擎的输出合并成统一的**候选元素集合**：

```python
def perceive(screenshot):
    texts  = ocr_screen(screenshot)          # [{text, box, conf}]
    icons  = detect_elements(screenshot)     # [{type, semantic, box, conf}]
    return merge(texts, icons)               # 屏幕候选元素集合
```

每个候选元素：**类型（文本/图标/控件）、内容（文字或语义）、位置框、置信度**。这份集合就是下一篇"看得懂页面"的原料——一堆散框如何变成"知道该点哪里"。
