# 02｜多 Agent 并行协作：任务拆解、失败处理与结果仲裁

> 「PalatMind 技术分享」系列第 2 篇。只谈理念，不含源码。

[返回目录](../README.md)

## 为什么要多 Agent

单 Agent 串行执行复杂任务有两大瓶颈：耗时线性叠加；上下文随步骤膨胀导致后期质量下降。拆分为子任务并行执行，能同时缓解这两个问题——但并行本身引入了新的复杂度：失败如何处理？结果冲突听谁的？

## 任务拆解：先有依赖图，再谈并行

主 Agent 拆解任务时必须输出显式的**任务依赖图**，包含：

- 子任务 ID 与描述
- 执行分配（由哪个子 Agent 负责）
- 依赖关系（哪些可并行、哪些必须串行）
- 预期输出格式

举例："同时打开音乐、视频、聊天三个应用并各执行一个操作"——三个子任务天然并行；"先联网调研再写报告"——必须串行。

**关键约束：禁止隐式上下文传递。** 子 Agent 之间不能靠"猜"共享信息，所有协作信息必须通过共享记忆或标准化消息显式传递。消息应包含：发送方标识、关联任务、消息类型（任务分配 / 进度 / 结果 / 错误）、载荷与时间戳。

## 失败处理：五级机制

子 Agent 失败是工程常态，不是异常。处理策略分层兜底：

| 机制 | 策略 |
|------|------|
| 重试 | 最多 3 次，指数退避（1s → 2s → 4s） |
| 降级 | 重试耗尽后，主 Agent 重新分解任务或自行承担该子任务 |
| 超时 | 每个子任务独立超时（默认 5 分钟），防止单点拖垮全局 |
| 熔断 | 同类子 Agent 连续失败 5 次，暂停该类型调度并记录错误 |
| 回收 | 主 Agent 崩溃或超时后，已分发子任务的结果超时自动回收至共享记忆 |

## 结果仲裁：冲突听谁的

多个子 Agent 对同一问题给出矛盾结论时，仲裁优先级从高到低：

1. **确定性计算**：数学结果、编译输出、数据库查询——机器说了算
2. **权威数据源**：官方 API 返回值、经过验证的知识库条目
3. **多数一致**：3 个以上 Agent 结论一致
4. **置信度评分**：各 Agent 自报置信度，取最高者

仲裁过程必须落审计日志：冲突描述、各方结论、仲裁依据、最终决策。事后可追溯，是排查"为什么 Agent 做了错误决定"的生命线。

## 进度感知：长任务不黑箱

桌面 Agent 常要运行几分钟到几小时。没有进度反馈，用户只有两种选择：干等，或者杀进程。我们的做法：

- 预估超过 1 分钟的任务，开始前汇报步骤总数与预估耗时
- 每完成一个里程碑推送进度（已完成 N/M 步）
- 实际耗时超过预估 2 倍时主动告警并询问是否继续
- 用户随时问"进度"，能实时汇总各子 Agent 状态给出整体报告

## 小结

并行带来的不只是速度，还有工程复杂度。显式依赖图、五级失败处理、确定性优先的仲裁、透明的进度反馈——这四件事做到位，多 Agent 才从"演示"变成"生产力"。
