# 05｜成功案例变脚本：让同类任务从分钟级到秒级

> 「PalatMind 是如何操作电脑的」系列第 5 篇。第一次成功靠"感知-理解-点击"逐步探索，之后的成功可以更快——把成功案例沉淀成自动化脚本。

[返回目录](../README.md#它是怎么操作电脑的)

## 第一次慢，是因为每一步都在探索

回看[第 4 篇](04-step-by-step.md)的执行流：每一步都要截图感知 → 理解定位 → 点击 → 确认。这是必要的——没有先例时，这是找到正确路径的唯一方式。

但「在酷狗搜歌并播放」这类任务，第二次、第三次执行时路径完全一样。每一步重新感知、重新定位，是在重复已经付过的探索成本。

## 成功后沉淀什么

任务成功的那一刻，执行轨迹就是一份现成的"操作说明书"。沉淀三样东西：

```yaml
script: kugou_play_song
precondition:            # 什么情况下这个脚本适用
  app: 酷狗音乐
steps:
  - act: click           # 步骤 = 操作 + 目标描述 + 验证锚点
    target: 搜索框
    verify: 光标出现
  - act: type
    text: "{song_name}"  # 参数化：歌名是变量
  - act: press_enter
    verify: 结果列表出现
  - act: double_click_row
    target: "包含{song_name}的行"
    verify: 播放栏出现{song_name}   # 最终锚点
```

**关键是每步都带验证锚点**——脚本不是盲目的动作序列，而是"每步可确认"的可靠回放单元。目标描述用自然语言+锚点存储，而不是死坐标（应用一更新坐标就全废）。

## 回放：跳过探索，直奔目标

同类任务再次到来时，直接按脚本回放：

- 不再逐步截图做全局感知，只在**关键节点做锚点确认**
- 参数代入（这次是《七里香》），流程复用
- **分钟级探索 → 秒级回放**，这就是"越用越快"的来源

## 脚本会失效：自愈与更新

应用会改版——按钮挪位、界面重构。死脚本的命运是悄悄失败，带锚点的脚本的命运是**当场发现并自愈**：

```python
for step in script.steps:
    if not locate(page, step.target):
        new_point = explore_relocate(step)   # 退回逐步感知，只对这一步重新探索
        step.update(new_point)               # 修复脚本，下次直接用
```

- 某步锚点找不到 → 只对这一步做局部重新感知定位，其余步骤照旧
- 定位成功 → 更新脚本中的这一步，**脚本随应用更新自动修复**，无需人工维护
- 局部修复也失败 → 整体退回第 4 篇的逐步探索模式；新的成功轨迹覆盖旧脚本

## 沉淀的纪律：只存成功

只有**最终验证锚点达成**的任务才允许沉淀脚本——失败的探索路径里没有可复用的成功模式。这条纪律保证了脚本库的每一个条目都是被验证过的路径，回放的成功率才有底气。
