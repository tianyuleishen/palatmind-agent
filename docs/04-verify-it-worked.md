# 04｜验证生效：防"假成功"的结果级验证设计

> 「让 GUI 自动化更精准」系列第 4 篇。自动化系统与玩具的分水岭，不在操作多花哨，而在能否诚实地回答：任务真的完成了吗？

[返回目录](../README.md#技术专栏让-gui-自动化更精准)

## 最危险的一句话："操作已执行，任务完成"

看一个所有做桌面自动化的人都踩过的坑：

> 任务：播放歌曲《晴天》。
> 脚本：定位到播放控件 → 调用成功 → 报告"播放完成"。
> 现实：点的是"播放"图标，但列表选中行是上一首；或者应用根本没出声。

每一步操作都真实执行了，任务却是失败的。这就是**假成功**——以"动作已执行"为完成标准，而不是以"结果已发生"为标准。

## 原则：从任务目标派生验证信号

验证条件不来自"我做了什么"，而来自"用户要什么"：

| 任务目标 | 动作级标准（错误） | 结果级标准（正确） |
|---------|------------------|------------------|
| 播放《晴天》 | 点击了播放按钮 | 播放栏/窗口标题出现「晴天」且状态为播放中 |
| 打开某网页 | 发出了点击链接的动作 | 浏览器标题/URL 变为目标页面 |
| 发送消息 | 调用了发送 | 消息出现在聊天记录列表中 |
| 保存文件 | 按 Ctrl+S | 目标路径出现新文件且修改时间为刚刚 |
| 复制文本 | Ctrl+C 按下 | 剪贴板内容与预期一致 |

**从目标文本中提取"验证锚点"**（歌名、页面标题、文件名、消息内容），再围绕锚点设计验证——这是整套机制的核心一步。

## 多通道验证：一个信号会骗人，五个不会

同一个"结果"可以从多个通道交叉确认：

| 通道 | 适用 | 示例 |
|------|------|------|
| 窗口标题 | 播放器/浏览器普遍把关键状态写进标题 | 标题含歌名 |
| 控件状态 | 控件树可读的应用 | 播放/暂停按钮的 ToggleState |
| 剪贴板 | 复制类任务 | ClipboardContains |
| 文件系统 | 保存/下载/整理类任务 | 文件存在 + mtime + 大小合理 |
| 视觉确认 | 上面全部不可用时的兜底 | 截图中出现播放栏 + 目标文本 |

组合原则：**优先可编程通道（标题/控件/文件），视觉做最后确认**。视觉验证有一个前置条件——截图必须来自真正的渲染窗口（见[第 1 篇](01-find-the-right-window.md)），否则"确认"本身建立在错误画面上。

## 两个容易漏掉的细节

**1. 验证太早 = 验证失败。** 点击播放后 50ms 就去读窗口标题，界面还没来得及更新。正确做法：等待 + 稳定期——验证条件在短窗口内（如 300ms）连续多次采样均成立，才判定通过；持续轮询直到超时，才判定失败。

**2. 失败要回流，不要假通过。** 验证失败后有两类系统：一类把差异信息（期望 vs 实际）注入上下文，修正后重试；另一类静默降级——"应用打开就算成功"。前者越跑越准，后者把不确定性攒到用户那里爆发。重试也应换策略：第一次点错了，第二次就先重新定位、检查遮挡、换点击级别，而不是原样再点一遍。重试预算耗尽后，**如实报告失败**——诚实的失败比虚假的成功有价值一百倍。

## 把验证做成通用能力，而不是逐任务硬编码

验证机制要能规模化，靠的是通用的**验证条件派生**：

```python
def derive_verification(task):
    anchor = extract_anchor(task)          # 从自然语言目标提取锚点（歌名/标题/文件名…）
    if anchor:
        return [
            WindowTitleContains(anchor),   # 通道 1
            VisualConfirm(anchor),         # 通道 2（基于渲染窗口截图）
        ]
    # 提取不到锚点 → 禁止降级为"应用在前台就算成功"
    return ExplicitConfirm()               # 交给用户确认
```

规则只有一条：**锚点存在 → 双通道强验证；锚点不存在 → 用户确认，绝不静默放行**。验证方式由通用逻辑派生，而不是按具体应用写死——换一个应用、换一个任务，机制不变。

## 系列小结：精准 = 四步各自做对

| 步骤 | 一句话 | 文章 |
|------|--------|------|
| 找对窗口 | 重选渲染窗口，DPI 全链路物理像素 | [01](01-find-the-right-window.md) |
| 找对元素 | 控件树优先，视觉兜底，兜底结果对齐回元素 | [02](02-find-the-right-element.md) |
| 点得中 | 等条件不 sleep，前台化验证，Pattern 优先 | [03](03-click-that-lands.md) |
| 验证生效 | 结果级锚点 + 多通道交叉 + 失败回流 | 本篇 |

四步各自做对，GUI 自动化才从"碰运气"变成"可交付"。
