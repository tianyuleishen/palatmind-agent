# 02｜看得懂页面：从一堆检测框到"知道点哪里"

> 「PalatMind 是如何操作电脑的」系列第 2 篇。感知给了你一堆散框，人眼里看到的却是"页面"——差距就在理解层。

[返回目录](../README.md#它是怎么操作电脑的)

## 散框不是页面

上一篇的输出是一堆候选元素：文本框、图标框、控件框。直接拿它们定位有两个问题：

- 同一个东西被拆成多块：一个按钮 = 图标框 + 文字框，不知道该点哪个
- 缺少上下文：列表里 20 行歌名，哪一行才是《晴天》？点歌名还是点行尾的播放按钮？

理解层做三件事：**布局分区、结构成组、状态理解**，然后才能精准回答"该点的元素在什么位置"。

## 一、布局分区：先建立页面骨架

按空间位置把元素归入功能区：

- **顶部导航栏**（横贯全屏顶部的元素带）
- **左侧栏**（纵向排列的菜单项）
- **内容区**（中部大面积的列表/卡片）
- **底部栏**（播放器底部控制条、状态栏）

分区不需要精确到像素，粗粒度即可——它的作用是给定位加**空间约束**（"搜索框应该在顶部区域"，缩小候选范围、排除误匹配）。

## 二、结构成组：把散框装进容器

这是理解层最核心的一步。

**1. 列表行识别**：同一水平线（y 坐标相近）、间距一致、样式雷同的元素聚成行——一行 = 图标 + 文本 + 行尾操作按钮。

```
[封面图] 晴天 - 周杰伦        03:55  [播放▶] [更多⋯]
[封面图] 七里香 - 周杰伦       04:58  [播放▶] [更多⋯]
```

**2. 父子包含**：文本框落在按钮框内部 = 这个按钮的文字；文本框落在输入框内部 = 输入框的当前值。包含关系一建立，"点按钮"自然变成"点包含这个文字的按钮"。

**3. 成组后，操作单位从"框"变成"行/卡片"**：点《晴天》这一行，就是先定位文本，再映射到整行，操作行内的播放按钮或整行本身。

## 三、状态理解：知道谁被选中、谁能点

- **选中态**：高亮背景/描边的列表行 = 当前选中项
- **可用态**：灰色 = 禁用，别浪费点击
- **输入态**：闪烁光标 = 输入框已聚焦，可直接打字

状态判断主要靠区域内颜色对比与图标差异，规则简单但对后续执行层极其重要。

## 四、目标定位：输出精确点击坐标

理解层最终的使命——给定目标描述，返回**该点的位置**：

```python
def locate(page, target):                     # target: "搜索框" / "《晴天》这一行"
    candidates = spatial_filter(page, target) # 用语义 + 空间约束缩小范围
    best = semantic_match(candidates, target) # 语义相似度选最优
    if best is None:
        return NOT_FOUND                      # 页面上没有 → 不硬点，交给执行层滚动/换页
    return best.click_point()
    # click_point 规则：
    #   按钮     → 按钮框中心
    #   文字入口 → 文本框中心
    #   列表行   → 行内主操作按钮；无按钮则整行中心
```

要点：

- **匹配不到就如实返回"看不见"**，绝不返回一个近似坐标去赌——这是精准的前提
- 同名候选多个时，用空间约束消歧（目标语义 + 期望区域 + 行上下文）

## 与 DPI 的交界

理解层所有坐标都在**物理像素**域运算。进程若不做 DPI 声明，系统会给它一套虚拟化坐标，视觉定位看起来正常、鼠标一动全偏——这是"自己机器准、别人机器偏"的最常见根因，务必在感知前统一坐标系。
