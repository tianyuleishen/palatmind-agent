# 03｜自我进化：技能沉淀、安全升级与回滚

> 「PalatMind 技术分享」系列第 3 篇。只谈理念，不含源码。

[返回目录](../README.md)

## 两个进化层次

桌面 Agent 的"进化"可以分两层：

1. **经验层进化**：不修改任何代码，通过沉淀技能、记忆、参数来加速——安全、日常、无感
2. **能力层进化**：修改自身的代码或运行时组件来实现新能力——高风险、低频、强管控

两层缺一不可：只有经验层，天花板低；只有能力层，风险失控。

## 经验层：技能提炼与加速

当同类任务**连续多次成功**，就值得问一句：这里面有没有可复用的模式？

以播放任务为例：首次执行需要探索应用界面（分钟级）；提炼成技能后（搜索 → 点击结果行 → 确认播放栏出现目标标题），再次执行是直接回放（秒级）。**首次探索的成本被摊销到后续所有同类任务**，这是我们定义"任务加速比"的出发点。

技能提炼的关键约束：

- **验证不通过的任务不提炼**——失败的流程里没有可复用的成功模式
- 技能必须与验证条件一起存储，回放后仍要走验证闸门
- 应用更新导致技能失效时，能检测失败并触发重新探索

## 能力层：自我修改的三道闸门

让 Agent 修改自身代码是终极能力，也是最危险的。我们的安全模型是三道闸门：

1. **沙箱闸门**：所有生成/修改的组件先在受限运行时中执行——资源计量（防死循环）、能力桥（只能调用显式暴露的能力）、结构化输入输出协议
2. **测试闸门**：修改后必须通过全量测试（单元 + 集成 + 回归），任何一项失败即拒绝升级
3. **人工闸门**：生成变更摘要，经用户审核授权后才执行构建与部署

## 回滚：升级失败是正常的

自我修改的工程成熟度，体现在回滚速度上：

- 每次升级前保存完整备份
- 新版本启动失败或测试回归 → 自动回退到上一个稳定版本
- 故障原因记录归档，成为下一次进化的输入

灾备恢复与审计日志同样必备：所有自演化变更（含回滚）必须可追溯。

## 评估驱动：进化要有仪表盘

"进化"如果没有度量就是自嗨。应持续跟踪的核心指标：

- 同类任务加速比（技能回放 vs 首次执行）
- 任务成功率（分场景）
- 升级后回归测试通过率
- 回滚触发率

每次迭代必须量化提升，才允许合入。

## 小结

自我进化的难点从来不是"让模型改代码"，而是**在不失去控制的前提下获得进化的收益**。经验层日常进化、能力层强管控、回滚机制兜底、评估体系导航——四件套齐了，进化才可持续。
